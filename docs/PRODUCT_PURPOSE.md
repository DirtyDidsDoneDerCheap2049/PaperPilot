# PaperPilot：研究方向空白探索需求与实现边界

更新：2026-09-23。本文是当前产品定位依据。历史研究报告、旧需求讨论和旧验收记录保留原文。

## 要解决的问题

研究者提出一个带有实现手段的创新方向，希望查清：哪些做法已经有人实现，自己的设想与最近工作差在哪里，剩余差异是否值得投入实验。如果证据不足，要知道该补查什么，不能把“未搜到”当成“没人做过”。

PaperPilot 是一个通用的论文研究方向解析 AI Agent，以桌面应用运行。研究任务围绕问题展开：拆出待核查主张，检索已有实现，批量解析论文，建立证据和覆盖关系，检查反证，收窄候选，给出最近工作差异与判别实验。用户可以补全文、提出新假设，在原会话继续。

受作者研究背景和当前验证范围所限，现阶段更适合深度学习方向的研究者使用。这是当前适用情况，不是对研究领域的功能限制。

一个方向往往涉及几十篇论文，处理这些论文是完成研究任务的手段。论文集不应预先限定全部检索范围，也不能靠处理篇数判断研究是否完成。文件工作区承载长期资料，同一会话保存一个方向的连续研究；当前尚无独立的“方向项目”数据库实体，不能只改 UI 名称就声称已实现。

一个典型输入是：“我想在科研文献检索中用证据一致性约束候选排序。已有工作做到哪一步？还有哪些差异值得验证？”不同领域的论文研究方向共用这条流程，不需要逐个开发专用功能。用户无需先准备完所有论文；选中或上传论文只是提供种子资料，不能改写问题或免除主动检索。

## 原始需求的具体含义

1. **方向要具体。** 原始表述要求“已经说明实现手段而不是比较模糊的只给出目标”。只写“提高精度”不够；应说明模块、机制和待核查差异。输入不明确时应帮助收窄，不能随意替用户决定方向。
2. **先查已有实现。** 检索既找支持材料，也找同义方案、功能等价做法和可能推翻新颖性的工作。几十篇资料仍可能漏掉最接近的一篇，数量不是停止依据。
3. **维护方向认识。** 工作区保留论文、证据、报告和讨论。新论文应能改变之前的判断；不能每轮只做互不相干的摘要，也不能把历史模型结论当作原文证据。
4. **对获取失败有反馈。** 主动尝试开放全文，标明未获取、未解析和证据不足；需要用户补 PDF 时给出标题和操作入口，用户也能反馈“没找到”。补充后应真正进入重新核查。
5. **能把想法往下推进。** 根据报告提出新机制时，应查相邻领域及其向目标任务的迁移工作，说明怎样缩小到可检验方案。通用模块拼接或一张空矩阵不能直接成为创新点。
6. **保留人的判断。** 输出已有覆盖、候选差异、反证、证据缺口、最近工作和判别实验；无合格候选可以是结果，但必须解释原因。论文问答和完整资料包方便用户或其他模型重新判断。
7. **用户能看见进度并继续工作。** 显示正在检索什么、处理哪些资料、何处失败和任务终态。桌面中的同一个对话应支持持续追问，不能要求另开脱离上下文的讨论界面。

最初是个人使用的双目立体匹配工具。按用户最新要求，现已删除或通用化全部立体匹配专项功能，统一方向解析、证据索引、覆盖关系和候选状态。立体匹配是一个普通输入任务，不再有固定论文补检索、专用分类矩阵或实验模板。产品目标是通用的论文方向解析，不按学科设置使用门槛；尚未验证所有学科的结论质量。

所有方向使用同一个证据审计器。蒸馏机制仍要求四项原文依据，迁移关系分别记录来源和目标任务，不预设模型类别。几十篇是需要覆盖的真实使用场景，不意味着每篇 PDF 全文一次塞进模型，也不意味着几十个模型请求无限并发。当前通过逐篇提取和每批最多 8 篇的证据审计进行综合；全文解析目前按顺序执行。

## 2026-09-23 再次纠正

前一轮把定位从单篇阅读改成了多论文联合分析，仍然把材料处理当成交付目标。50 篇合成 PDF 测试可以验证流程，却无法回答“这个方向有哪些值得研究的空白”。这是产品判断和验收选择的问题，不是只少写了“空白”两个字。

本次已修改的行为：

| 位置 | 发现的偏差 | 修正 |
|---|---|---|
| `src/ui/static/workbench.js`、`desktop.js` | 首页中心是联合分析一组论文，主要提示处理篇数 | 研究方向与实现想法作为入口，展示已有实现、反证、候选和验证步骤；导入作为补充材料 |
| `src/agents/orchestrator.py::_search` | 累计 50 条就中止，后面的检索问题可能未执行 | 按配置查询预算执行，记录实际查询与预算外查询；仍不声称穷尽文献 |
| `src/analysis/evidence_grounded.py` | 所有方向都强制套用蒸馏矩阵与实验模板 | 最新修正：全部方向使用 `direction_coverage.py` 的主张与方法关系证据索引，专项分支已删除 |
| 非蒸馏候选核查 | 与方向无关的教师字段可能决定候选命运 | 要求本轮最近工作、有效原文证据 ID、具体差异和判别实验；不满足则暂缓，仍需 Critic 裁决 |
| `_latest_research_context` | 历史消息截取开头可能丢失报告后半段的候选 | 从最近研究记录补入正式、待验证和否决候选及所缺证据，保留历史状态 |
| `_generate_report`、`critic.py` | 推荐步骤固定偏向教师冲突、蒸馏或门控 | 新报告先列研究问题和范围，保留方向对应的实验；通用方向显示主张与证据表 |

没有自动把旧报告重新算成新结论。用户在原会话发起新研究后才使用新逻辑，旧报告仍可按原版本查看。

此前仍有价值的工程修改：

| 范围 | 偏差与处理 |
|---|---|
| 产品定位、README、首页 | 之前强调阅读工作区与问答，弱化了多论文 Agent。改为研究方向、论文集合、跨论文分析和持续研究主线。 |
| 历史会话模式 | 本轮早先无条件切到普通问答，导致继续研究不再触发检索。现在根据最后一条 assistant 消息的模式恢复，旧研究报告默认研究 Agent。 |
| 全文处理范围 | 本轮早先引入严格 30 篇硬上限，默认仍只有 10 篇。现在可配置 0–100 篇，新工作区默认 50 篇；尊重旧工作区显式设置，用户可在设置中调整。 |
| 任务预算 | 本轮早先固定 64 次请求、30 分钟。现在设置中可配置，默认 200 次、120 分钟，提交时保存预算快照，执行进程使用同一快照。它们是边界，不是耗时或费用承诺。 |
| 批量入口 | 单文件上传改为一次选择多个 PDF，逐项反馈成功或失败，成功项加入待研究集合。 |
| 连续研究 | 同一会话承接上一份研究报告的论文集合，并合并本次新增论文，再扩展检索；要切换独立方向可新建研究。 |
| 覆盖透明度 | 逐篇列出已审计全文/摘要、未分析、提取失败、审计失败和暂排除。不能因为报告生成成功就声称所有论文已分析。 |
| 报告完整性 | 去掉选中论文、全文论文和缺全文清单的前 15/20 篇截断，以及画像表前 30 篇截断。 |
| 验收 | 增加 50 篇合成 PDF 的解析、画像、分批审计和报告回归；另检查限制为 12 篇时剩余 38 篇全部有状态。单篇样例不代表多论文主流程验收。 |

## 保留的工程改造

C++ 持久任务、Python 分析进程、取消与中断记录、幂等、本地数据隔离、默认 SQLite、可选 MySQL、自带 API、密钥保护、历史导入、备份和开源分发都服务于原目标。没有必要为了纠正定位把这些全部撤销。桌面使用仍无需注册本项目账号或部署服务器。

已有的证据来源校验、严格蒸馏判定、方向约束和反证门保留。不能为了让报告显得有产出而降低真实性标准；没有合格创新候选是合法结果。

## 仍然不能声称已完成的能力

- 当前是固定阶段的 Agent 编排，不是能够自行制定任意研究计划、反复扩展检索直到问题解决的通用自主研究系统。
- 单个研究任务中 PDF 处理和画像提取主要顺序执行；多篇输入与跨篇分析不等于已实现并行 Subagent 调度。
- 提取器对单篇文本有 60,000 字符限制。长文后半部分、附录和表格可能没有完整进入模型，不能宣传“全部论文逐字精读”。
- 跨论文综合仍受模型上下文和输出长度限制；已保留逐篇状态，但分层综合和按需回读原文尚需专门实现与评测。
- 获取全文依赖来源与访问权限；补 PDF 是明确降级路径。当前没有验证几十篇真实论文的自动获取成功率。
- 已解析文本可复用；任务重试仍从流程起点执行，并非任意步骤精确恢复。画像、报告和任务数据库还存在跨存储提交窗口。
- 默认本地文本检索便于安装，但不是语义向量检索的等价物。可选向量组件、SessionRAG 和 RecoveryManager 文件存在不构成主流程完整接线的证明。
- 50 篇合成材料回归只验证覆盖和流程。真实论文结论、引用解释、创新判断、在线耗时和费用还需要使用记录与人工核查，不能写成已测准确率或生产能力。

通用方向的主张覆盖索引只解决“已有证据不能因为不是蒸馏而消失”的问题。它还不是能够为任意方向自动设计高质量实现维度的研究地图，也不能替代原文核查。

## 按研究目标验收

| 场景 | 应有结果 | 当前验证方式 |
|---|---|---|
| 已有 50 篇资料，尚有待核查检索式 | 在查询预算内继续执行，不因数量足够而提前停 | 离线检索回归 |
| 研究融合或迭代方法 | 有原文依据的主张进入覆盖索引，不要求论文必须做蒸馏 | 非蒸馏合成证据回归 |
| 引用编号不存在、只有摘要、审计失败 | 不产生直接覆盖或正式候选 | 失败与降级回归 |
| 模型未给出 Critic 逐项裁决 | 候选留待验证 | 候选状态回归 |
| 在旧会话追问报告里的点子 | 方向、候选状态和待补证据进入上下文 | 真实数据库结构的历史恢复回归 |
| 有可信最近工作和窄义差异 | 报告可追溯到证据，给出可证伪实验 | 仍需真实论文人工标注与在线评估 |

离线测试使用合成原文和假模型，只能证明控制逻辑与证据约束，不能证明研究结论正确。

## 后续仍需实施的研究能力

1. 围绕一到两个具体方向建立人工核查样例：标注最近工作、已有实现、易混淆方法、允许保留的候选及不能下结论的原因。验收覆盖遗漏和反证误判，不能只看报告是否生成。
2. 把候选的 `required_evidence` 变成有预算的补检索任务，增加“查到反证后修改主张、再决定继续或停止”的循环。目前需要用户明确发起下一轮。
3. 对长文和关键主张按需回读，记录页段与来源版本；再验证新全文能否改变旧判断。
4. 保存方向、候选和证据变化历史，区分“新资料推翻旧判断”与“模型重新措辞”。目前保存报告版本和状态，尚无完整结论差异追踪。

这些是原产品目标中尚未完成的部分。C++ 任务内核、数据库和桌面打包支持这条研究流程，不能用它们代替研究能力验收。
